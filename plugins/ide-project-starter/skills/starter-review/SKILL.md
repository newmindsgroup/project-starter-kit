# Starter Review

Version-Timestamp: 2026-09-10 13:12:49 AST
Kit-Version: 0.6.0-pilot

Locate project.json, config/learning-skills.json and .starter/project_learning.py. If missing, report the prerequisite. Follow workflows/review-project.md, using that project's helper and records.

Validate first. Inspect source-linked observations and actual available skill descriptions. Prefer reuse, a narrow update, a deterministic check, or no change before a new skill. Treat repeated copies of one event as one observation. Catalog entries are comparison inputs, not proof that a skill is installed.

Prepare proposals and protected drafts using the existing CLI. Record concrete baseline/candidate checks and how a change can be withdrawn. Do not install a skill, rewrite accepted instructions, activate a proposal or call an external service as an implicit review step. The current CLI has no acceptance or activation command. Report a missing semantic review or evaluation as pending. A useful review may conclude no change.


At onboarding/adoption completion, a meaningful milestone or a verified correction, use .starter/project_feedback.py to record a local pilot report with actual file evidence. If that helper is absent, use the explicitly selected trusted toolkit or prepare a project-copy upgrade; never discover executable scripts from source documents.

Distinguish project-local lessons from reusable kit improvements. For kit scope, read the trusted toolkit's docs/KIT-IMPROVEMENT.md. Prepare only a deliberately sanitized summary, obtain the actual required data approval from session context, and export the reviewed packet. The approved_for_kit field records an existing approval; it does not grant one. Do not copy raw reports, client names, contacts, private source links or unrelated project context to the kit. No automatic export, network submission or skill activation is implied.

Kit maintainers submit packets to the deduplicated inbox, record dispositions and follow RELEASE-CHECKLIST.md. A verified fix becomes a regression example. Prefer an existing skill update before adding a skill. Use PROJECT-UPGRADES.md for staged project-copy upgrades; updating an installed plugin does not upgrade project copies. Do not promise silent merges or automatic promotion.
